# T8 修复工单：旧局恢复请求覆盖新局

**状态：已修复并验收（2026-10-16）。** 原优先级 P1；修复前阻断 T8 验收。修复提交：`5d3854f`、`ece3ca2`。

## 原问题（修复前）

页面加载时，`frontend/src/App.vue` 的 `onMounted(recover)` 会从 `sessionStorage` 读取旧局并发起 `GET /api/v1/games/{id}`。在该请求尚未返回时，用户可以点击“开始一局”，发起 `POST /api/v1/games`。如果新局先创建成功，旧局 GET 后返回，`recover()` 会无条件执行 `clearGame()`、`setSession(old)` 和 `applySnapshot(old)`，覆盖刚创建的新局。它先清空状态，因此 `state/game.ts` 的旧局快照守卫无法阻止覆盖。此时页面显示旧局，但 `sessionStorage` 仍保存新局 ID 与令牌。

若旧局 GET 在新局创建后以 404 等错误结束，`recover()` 的 `catch` 又会无条件删除 `sessionStorage`、清空新局并显示旧请求的错误提示。两种结果都违反“迟到的旧局响应不得替换新局”。

## 稳定复现（修复前）

1. 在 `sessionStorage['guandan.session']` 保存旧局 `game_id` 和令牌；刷新页面，并延迟旧局 GET 响应。
2. GET 未完成时点击“开始一局”，使创建请求先返回新局 `game_id`、令牌和快照。
3. 放行旧局 GET。成功响应会让页面退回旧局，失败响应会清掉新局；前者还造成页面与存储中的局 ID 不一致。

审查时曾以临时 Vitest 组件测试控制两条 Promise 的完成顺序，复现了“页面显示旧局、存储仍指向新局”；该诊断文件未留在仓库。

## 预期行为与修复范围

- 用户新开局后，旧恢复请求的成功或失败结果都不得修改新局的页面状态、提示或 `sessionStorage`。
- 没有新开局时，正常恢复仍可用；旧局确已失效时，仍显示“本局已失效，请重新开始”并清理旧会话。
- 在 `recover()` 的成功和失败分支都校验请求发出时的会话/请求代次是否仍为当前会话；过期响应直接忽略。可使用递增代次、会话身份检查或取消请求，但仅依赖 `applySnapshot()` 不够，因为目前调用前会先 `clearGame()`。
- 改动以 `frontend/src/App.vue`、必要的状态辅助方法与组件级回归测试为限，不改后端 API 合同。

## 验收测试

1. 延迟旧局 GET；新局创建先成功；旧局 GET 后成功：页面与 `sessionStorage` 均保持新局，不出现旧局数据。
2. 同样时序下，旧局 GET 后返回 404/网络错误：新局不被清除，不显示旧局错误。
3. 没有并发新建时，正常刷新恢复及旧局失效提示保持有效。
4. 运行 `npm run test:unit -- --run`、`npm run typecheck`、`npm run build`；提供测试数量与结果。

## 修复与复验

- `recover()` 在请求发出前记录会话代次；新局创建成功后递增代次。旧恢复请求若在新局创建后才返回，其成功与失败结果均被忽略，不再覆盖页面、存储或提示。
- 新局创建成功时清除旧恢复请求可能在创建期间写入的提示；创建请求在途时忽略重复点击，避免两个创建响应乱序覆盖。
- `frontend/src/__tests__/recovery-race.test.ts` 覆盖旧局迟到成功、迟到 404、旧局错误先于新局成功、连续点击，以及正常恢复与旧局失效提示。
- 2026-10-16 复验：前端 14 项单测通过，`npm run typecheck` 与 `npm run build` 通过；后端常规测试 250 项通过。T8 可结束，开始 T9。
