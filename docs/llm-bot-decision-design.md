# 大模型机器人出牌决策方案

日期：2026-11-17

状态：阶段 A 已实施（异步本地策略）；B–E 待实施

## 目标与边界

让大模型为三个机器人选择出牌策略，同时保持后端对规则、回合、隐藏信息、版本和幂等性的权威控制。模型只在服务端给出的合法候选中选择；它的输出不能直接修改牌局状态。模型不可用时，牌局应在明确的时限内由本地策略继续。

本方案不改变 `gd-v1-level2` 的规则、真人固定座位 0、机器人座位不开放给客户端等约定。模型提供商和具体模型暂不固定。

## 现有架构及改造原因

- `GameEngine.getLegalActions` 生成机器人的全部合法动作：领出时没有过牌，跟牌时加入过牌。`RandomLegalPolicy` 从列表中等概率抽取一项。
- `PlayerViewFactory` 只给行动者自己的手牌、各家余牌数及公开桌面信息，不包含其他人的未出手牌或游戏种子。这个边界应延续到模型输入。
- `GameService.submit` 在每局锁内执行真人动作及后续整批机器人动作，成功后一次提交状态、事件和幂等结果；异常则整批回滚。现有 `BotPolicy` 是同步接口。不能直接在持锁期间调用远程模型，否则模型延迟会阻塞该局的状态读取、重试和其他请求。
- 实测 `legal-actions` 最多曾产生 3,270 个候选。将完整列表直接交给模型会增加延迟和费用，需要独立的候选整理层。

保留“真人动作 + 机器人批次一次提交”的事务语义，改为异步计算工作副本、完成后原子提交。批次尚未提交时，对外只返回上一份已提交的牌局状态，以及该命令的处理中状态。

## 后端模块

| 模块 | 职责 |
| --- | --- |
| 规则引擎 | 生成合法动作、校验声明并推进状态；任何策略都不能绕过 `GameEngine`。 |
| 决策编排器 | 按回合构造机器人视图和合法动作，协调模型调用、校验、兜底与批次截止时间。 |
| 候选整理器 | 从完整合法列表构造有代表性的有限候选，为每项分配仅在本次决策有效的 `candidate_id`；保留出完手牌、过牌及关键牌型等类别。候选数量和筛选规则通过对局评测确定。 |
| 模型适配器 | 发送结构化输入，接收形如 `{"candidate_id":"c17"}` 的结构化结果；处理超时、限流和提供商错误。 |
| 本地兜底策略 | 初期复用 `RandomLegalPolicy`；若未来改成启发式策略，应单独测试和评测。 |
| 命令状态存储 | 保存 `request_id`、请求体指纹、起始版本、处理中/完成状态、工作任务所有权、截止时间和最终响应。 |

模型输入仅包括当前机器人的 `PlayerView`、可公开的本轮历史、规则摘要及候选动作的公开描述。不得传入完整 `GameState`、其他座位未出的手牌、会话令牌或游戏种子。服务端将模型返回的 ID 映射回本次候选及完整合法动作，并再次按座位与状态版本核对。

## 正常链路

1. 浏览器提交真人命令，携带 `request_id` 和 `expected_version`。
2. 服务端鉴权并取得每局锁，先查已完成或正在处理的同 ID 命令，再核对请求体指纹、版本及真人动作。合法后登记处理中任务，在私有工作副本应用真人动作，释放锁，返回 `202` 与 `request_id`。
3. 工作任务循环处理机器人回合：生成完整合法动作和机器人专属视图，整理候选，调用模型并限定单次及整批耗时；校验返回的 `candidate_id`，然后由 `GameEngine` 执行。直到再次轮到有牌的真人，或牌局结束。保留现有 512 步上限。
4. 工作任务重新取得每局锁，核对起始版本和任务所有权；一次提交最终状态、按序事件及幂等响应，标记命令完成。
5. 浏览器通过带鉴权的命令状态接口查询结果；完成后取得与现有 `CommandResponse` 等价的最终状态和事件，逐步展示机器人行动。`GET /games/{id}` 应额外标明是否有处理中命令，避免刷新后把旧状态误认为可行动。

同一 `request_id` 与相同请求体在处理中时返回同一任务状态，完成后返回同一最终结果；同 ID 不同请求体仍返回 `REQUEST_ID_REUSED`。该局有未完成任务时，其他真人动作必须被拒绝或明确要求稍后重试。前端在收到 `202` 后显示“机器人思考中”，禁用出牌/过牌，并在刷新后继续查询同一命令；网络结果不明时仍使用原 `request_id` 重试或查询。

## 异常与兜底

| 情况 | 处理 |
| --- | --- |
| 模型超时、网络故障、429、额度耗尽或服务不可用 | 为单次决策和整个批次设置可配置截止时间；超时即选用本地合法策略。连续失败时短时熔断，直接走本地策略。整批剩余时间不足时不再发起模型请求。 |
| 输出格式错误、未知候选、重复/过期响应 | 丢弃模型结果，用本地策略从当前完整合法列表选择。不能执行模型自行给出的牌 ID 或声明键。 |
| 浏览器断线、刷新或重复提交 | 以同一 `request_id` 查询或重试，返回处理中状态或缓存结果，不重复扣牌。 |
| 工作任务异常退出或超过截止时间 | 看门狗回收任务所有权；从未提交的批次起点重算，必要时全程使用本地策略，防止牌局永久停在处理中。提交时核对任务所有权，拒绝迟到任务写入。 |
| 规则引擎拒绝已核验动作、状态版本不符或超过步数上限 | 视为服务端一致性故障，整批回滚并告警；不靠反复随机选择掩盖规则错误。 |
| 进程重启 | 当前 `InMemoryGameStore` 会丢失整局和任务，沿用现有旧局失效提示。若要求重启后续局，需将牌局状态、处理中任务、事件、会话及幂等结果一起持久化，并保证原子提交。 |

模型错误与规则错误应分开统计。日志记录决策耗时、模型/提示词版本、候选摘要、最终采用的动作、兜底原因和费用，不记录会话令牌或不必要的完整手牌。复盘使用**实际采用的动作序列**驱动规则引擎，不能再次询问模型来重演历史。

## 实施与验收顺序

1. 先让现有本地策略经过异步编排器运行，补齐 `202`/状态查询、刷新恢复、同 ID 幂等、批次提交和看门狗测试；此阶段不接模型。
2. 增加候选整理与模型适配器，使用固定响应和故障注入测试合法 ID、无效输出、超时、限流、迟到响应及熔断。
3. 在固定洗牌种子上与随机基线对局，比较非法动作数、完整对局率、胜率、耗时及单局费用；灰度启用，并监控模型延迟、兜底率、无效输出率和任务积压。
4. 公开使用前，结合活跃牌局上限和创建限流限制模型并发与费用；确认模型密钥仅保留在服务端。是否需要跨重启续局，按公开上线计划另行决定。

## 方案选择与兼容策略

| 路径 | 好处 | 代价 | 结论 |
| --- | --- | --- | --- |
| 在现有 `BotPolicy` 中同步请求模型 | 改动少，原 `200 CommandResponse` 不变 | 网络等待占用每局锁与请求线程；一批可能包含多次模型调用，超时难控制 | 仅适合一次性实验，不作为正式实现。 |
| 异步计算私有批次，完成后一次提交 | 保留现有整批原子性；锁不跨网络请求 | 增加处理中命令、查询接口、前端恢复和任务监护 | **推荐**。 |
| 每个机器人动作立即提交并推送事件 | 真正实时展示 | 改变当前整批回滚和幂等合同，断线恢复更复杂 | 留待未来独立版本。 |

默认策略仍为 `random`，新异步流程先通过开关在测试及灰度环境使用。每局创建时固定本局策略，运行中改配置不改变已有牌局。模型服务未配置或熔断时选择本地策略，不影响纯本地玩法。保留 `POST /actions` 在 `random` 模式下原有的 `200 CommandResponse`；异步模式可返回 `202`，完成后同 ID 重试返回原有 `200 CommandResponse`。

## 命令状态机与 HTTP 合同草案

命令状态为 `PENDING → COMPLETED | FAILED`，可另有内部 `RUNNING`；每局同时最多一个未完成命令。`202` 表示请求已登记，**不表示真人动作已经提交**。外部牌局在完成前保持上一个已提交快照。命令终态写入后不可再改。

| 请求 | 建议响应 | 关键语义 |
| --- | --- | --- |
| `POST /api/v1/games/{id}/actions` | 同步路径仍为 `200 CommandResponse`；异步登记或同 ID 处理中为 `202 {request_id, status:"PENDING", poll_after_ms:500}`；同 ID 失败重试为 `200 {status:"FAILED", error:{code,message}}`；执行器队列满返回 `503 COMMAND_QUEUE_FULL`（任务已清除，可原 ID 重试） | 沿用现有 Bearer 认证、请求体指纹和先查幂等再查版本的顺序。 |
| `GET /api/v1/games/{id}/commands/{request_id}` | `202` 处理中；`200 {status:"COMPLETED", result:CommandResponse}` 或 `200 {status:"FAILED", error:{code,message}}`；未知 ID 为 `404 COMMAND_NOT_FOUND` | 仅本局令牌可查。查询不触发第二次执行。`FAILED` 表示已回滚，用户可刷新后发起新命令。 |
| `GET /api/v1/games/{id}` | 现有 `GameView` 增加可选 `processing_request_id` | 处理中返回旧快照，但前端必须保持操作锁并继续查询该命令。无处理中命令时字段缺省。 |
| `POST /resolve`、`GET /legal-actions` | 本局处理中时 `409 GAME_BUSY` | 避免对即将改变的旧快照继续解析或给出提示。 |

注：`503 COMMAND_QUEUE_FULL` 为实现期（阶段 A）新增的错误码，已同步至 `docs/api-v1.md` 的错误码表与异步命令模式章节。

同 ID 不同请求体继续返回 `409 REQUEST_ID_REUSED`；不同 ID 在本局处理中返回 `409 GAME_BUSY`，错误详情仅包含正在处理的 `request_id` 与建议等待时间，不包含手牌或令牌。`GET /commands/{id}` 的 `COMMAND_NOT_FOUND` 可能表示原 `POST` 根本没有登记，前端应以**原请求体和原 ID**重发 `POST`，不能生成新 ID；`GAME_NOT_FOUND` 则表示整局失效，应走已有的重新开局提示。终态 `FAILED` 也按同 ID 幂等缓存，不再执行旧命令；用户确认旧状态后用新 ID 发起新命令。所有新增路由仍由 `SessionAuthInterceptor` 在请求体解析前鉴权。更新 `docs/openapi.json`、生成的前端 schema 和 `docs/api-v1.md` 时，把异步响应标为新增合同，不能把旧同步响应悄悄删掉。

### 单局记录与任务所有权

在 `GameRecord` 中新增一个当前任务记录，包含 `request_id`、不可变请求指纹、起始状态版本、任务代次 `generation`、截止时间和状态。所有字段仍只在该局锁内访问；不要通过 `volatile state` 直接读写其他可变字段。登记任务时验证真人动作并保留原始已提交状态；异步工作只处理由该状态派生的私有工作副本。提交时必须在锁内同时核对：仍是同一个任务 ID、同一代次、同一起始版本。原子写入最终状态、事件、事件序号、幂等响应与 `COMPLETED` 状态，然后释放该局任务占位。

线程池容量和队列必须有界。成功登记任务但提交给执行器失败时，要在返回前清除该任务并返回可重试错误，不能留下永远 `PENDING` 的局。模型调用不得持有每局锁。请求超时只取消等待；迟到的 HTTP 响应及旧任务必须在代次核对处被丢弃。

看门狗到达整批截止时间后使原任务代次失效，使用原始已提交状态和同一真人动作重算整批，剩余机器人动作全部使用本地策略。旧工作任务即使稍后完成也不能提交。任务和终态缓存随牌局一起清理，不能无限增长；清理前须保证尚在运行的工作任务失去所有权。当前进程内存模式下服务重启仍使整局失效；未来若改持久化，任务领取、状态和幂等账本必须进入同一可靠存储与事务。

### 前端恢复规则

`frontend/src/api/game.ts` 需要把 `200` 与 `202` 解析成明确的联合结果，不能把 `202` 当作已完成的 `CommandResponse`。`frontend/src/state/game.ts` 继续保存 `{game_id, command}`；收到 `202` 后保留 pending、显示“机器人思考中”，以可取消的轮询查询命令状态。查询完成后走现有最终快照和事件播放路径，只有确认 `COMPLETED` 才清除 pending。查询失败时保持锁定并允许原命令重试；切换新局后丢弃旧查询结果。刷新恢复先查询命令状态，再决定是否采用 `GET /games` 的快照；`processing_request_id` 用于本标签没有 pending 记录时恢复等待。轮询间隔先采用响应中的 `poll_after_ms`，页面离开或游戏切换时停止旧轮询。

## 模型决策合同与初始参数

决策输入由服务端构造：`rule_profile_id`、行动座位和队伍关系、该座位自己的实体手牌、四家余牌数、当前有效牌、有限条公开事件、`state_version`、本轮候选摘要。公开事件只取已有公开事件，不读取其他座位未出的手牌。不要传游戏 ID、会话令牌或游戏种子给模型。规则摘要应包含固定打 2、搭档座位 0/2、领出与跟牌、炸弹等核心比较规则；提示词版本独立记录，不能让模型改写规则。

候选先由 `GameEngine.getLegalActions` 完整生成，再用稳定顺序形成有界列表。初始上限建议 **48 项**，作为待测配置值：若合法则始终纳入 `PASS`；优先纳入一手出完、各牌型的较弱及较强代表、炸弹体系和不同百搭消耗；剩余名额按固定规则补齐。候选 ID 只在这次 `state_version + seat` 决策内有效。若合法动作不足 48 项，全部发送。不得仅截取生成器排序前 48 项，否则会系统性漏掉后面的牌型。需统计完整候选数、入选数及各类覆盖率，避免筛选器使模型永远看不到好牌。

模型只返回 `candidate_id`；可选说明仅用于诊断，不参与执行。JSON 结构不匹配、候选不在本次列表或状态已过期，都视为模型失败。最后使用完整合法动作表查回 `Action`，由 `GameEngine.applyAction` 再校验一次。可设计 `BotDecisionGateway.decide(context)`、`CandidateSelector.select(fullActions, context)` 与 `BotBatchRunner.run(snapshot, command)` 三个边界；具体类名可按仓库命名调整，但规则层不得依赖模型 SDK。

初始保护值建议单次模型等待 **4 秒**、整批 **12 秒**、每局一个任务、全局最多 **4 个同时模型请求**、候选上限 **48**；这些是开发配置起点，**不是现有性能保证**。模型网关设置连接/读取截止、最大响应字节数和严格 JSON 解析；服务端凭据由部署配置注入，不进源码、浏览器、URL 或日志。任何队列满额、并发额度不足或预算耗尽都直接走本地策略，不让已登记命令无限排队。

## 方案目前的不足与验证办法

| 不足或风险 | 影响 | 落地前验证 |
| --- | --- | --- |
| 尚未选定模型提供商、协议、凭据与部署区域 | 无法完成真实网络适配和费用核算 | 先以可注入的假网关完成编排；选定提供商后单独实现适配器并做契约测试。 |
| 48 项短名单可能漏掉关键动作 | 模型即使判断正确也无法选到最佳牌 | 固定种子对局和人工复杂手牌评测候选覆盖；必要时分层筛选或提高上限。 |
| 原子整批提交让机器人动作只能完成后播放 | 用户会先等待，再看到“逐步播放”，并非实时思考过程 | 用真实模型测单局等待分布；若体验不佳，另立逐步提交方案，重新定义回滚与恢复合同。 |
| 随机兜底合法但不聪明，也可能有牌可压却过牌 | 故障时胜率和搭档体验下降 | 先保持现有行为以控制改造范围，再独立比较启发式兜底。 |
| 当前内存牌局与任务无法跨进程恢复 | 重启会让处理中和已完成的整局一并失效 | 按公开上线计划决定是否引入持久化，不把看门狗误称为跨重启恢复。 |
| 模型请求和批次重算可能重复计费 | 迟到调用虽不能提交，仍可能已经消耗额度 | 为每局、全局设调用预算与指标；超时后停止继续发起模型调用。 |
| 候选和命令终态会随牌局累积 | 公网使用时内存可能持续增长 | 与活跃牌局过期和回收一起设计任务取消、缓存清理及压测。 |
| 旧同步 API、前端 pending/动画逻辑耦合较深 | 兼容回归范围大，尤其响应丢失与旧结果迟到 | 在随机模式保持旧合同，新增异步 E2E 覆盖刷新、双击、超时、跨局与结算。 |
| 尚无模型质量目标与真实成本数据 | 不能声称模型比随机策略强或可负担 | 以相同种子运行随机基线和模型策略，报告胜率、完整对局率、平均/尾延迟、兜底率和每局费用。 |

本节的参数和 HTTP 形态是供 Qoder 实现的**建议合同**；若实现时发现与现有代码冲突，应先更新本文和 API 文档，再改代码。模型提供商及真实凭据没有确定之前，不能把“假网关测试通过”写成“真实模型已接入”。
