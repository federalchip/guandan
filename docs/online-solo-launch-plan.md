# 掼蛋单人版小规模公开上线计划

日期：2026-10-20
状态：方案草案，尚未实施

## 目标与首版假设

任何人都能通过网页开始一局；每局由 1 名真人和 3 名机器人参与，玩家之间互不影响。首版预计只有少量用户，按最多约 10 局同时进行设计，使用单台服务器和单个后端实例。首版允许服务器重启后旧局失效，玩家重新开局；是否需要跨重启续局，依据试玩反馈决定。

“约 10 局”是容量规划初值，不代表已经测得的性能上限。正式上限应由并发压测确定。当前不增加账号、多人联机、排行榜或付费功能。

## 阶段 1：资源保护与公开访问

当前 `backend/src/main/java/com/guandan/service/InMemoryGameStore.java` 将牌局、令牌和幂等记录保存在进程内，已结束或放弃的牌局不会回收；创建牌局接口无需会话令牌。公开访问前先完成：

- [ ] 为创建牌局接口设置按来源 IP 的频率限制；经反向代理时只信任指定代理传来的真实 IP。
- [ ] 设置同时活跃牌局上限；满额时返回明确的状态和用户可读提示，已有牌局仍能继续。
- [ ] 给闲置牌局与已结束牌局设置过期时间，清理时同步移除牌局、令牌索引、事件和幂等缓存。
- [ ] 限制请求体大小和单次处理时间，避免异常请求占满服务资源。
- [ ] 为限流、满额、过期、清理与并发创建编写后端测试；前端展示对应提示。

初始参数建议从“10 局同时活跃、创建接口每 IP 每小时 3 次、闲置 2 小时、结算后保留 1 小时”开始试运行。共享网络的用户可能共用 IP，因此应根据实际使用情况调整限流值。

**验收：**反复创建或刷新不会造成内存持续增长；超过上限时新用户收到清楚的提示；已建立的局不被其他访问者影响。

## 阶段 2：功能、性能与安全验收

本地单局的 T10 自动对局与 T11 桌面浏览器交付验收已完成，证据见 [测试报告](test-report-v1.md)。公开上线前仍需针对部署环境补齐：

- [ ] 用大量不同洗牌种子跑完整自动对局，检查无非法动作、死循环、机器人步数越界或错误结算。
- [ ] 真实浏览器覆盖桌面和手机：开始、选牌与声明、出牌、过牌、观察各座位、结算、刷新恢复。
- [ ] 验证弱网、重复提交、断网重试、旧响应迟到和服务重启后的失效提示。
- [ ] 以约 10 局同时进行作为初始压测场景，记录响应时间、错误率、CPU 与内存峰值，据结果确定容量上限。
- [ ] 检查公开 API 只返回本人手牌和各家已打出的公开牌；检查会话令牌不出现在日志、URL 或错误响应中。
- [ ] 检查依赖漏洞和生产安全响应头；所有会话请求均通过 HTTPS。

**验收：**自动对局和浏览器核心流程通过；并发试玩中不串局、不泄露未出手牌、不出现持续增长的资源占用。响应时间目标在首次基准测试后确定，不预设未经测量的数值。

## 阶段 3：生产部署

当前 `frontend/vite.config.ts` 的 `/api` 代理仅供本地开发。生产环境采用同源部署：反向代理在同一域名下提供前端静态文件并将 `/api` 转发给一个 Spring Boot 实例。

- [ ] 构建并固定版本的 `frontend/dist` 与后端 JAR；准备独立的生产配置，不使用 Vite 开发服务器承载用户流量。
- [ ] 配置域名、HTTPS 证书、HTTP 跳转 HTTPS、反向代理和必要的超时设置。
- [ ] 将后端交给服务管理器运行，配置开机启动与异常退出后的自动重启。
- [ ] 制定发布和回滚步骤：先验证构建与测试，再发布；保留上一版本构建物；发布失败可回滚。
- [ ] 部署后从公网执行健康检查与完整的“开始到结算”冒烟测试。

**验收：**用户通过域名可以完成一局；刷新可恢复仍有效的局；HTTP 自动转 HTTPS；发布失败能够恢复上一版本。首版保持单个后端实例，因为内存牌局不能在多个实例间共享。

## 阶段 4：运行与故障处理

- [ ] 区分进程存活检查与业务就绪检查，并由部署环境执行探活。
- [ ] 记录结构化错误日志、请求耗时、5xx 数量、活跃牌局数、内存和 CPU；日志屏蔽完整会话令牌与手牌。
- [ ] 为服务不可用、错误率升高和内存接近上限设置通知。
- [ ] 写明启动、停止、发布、回滚、日志查看与故障排查步骤，并演练一次进程故障和一次回滚。
- [ ] 在前端对服务暂不可用、局已过期和容量已满给出明确提示。

**验收：**进程异常退出后能恢复服务；故障可通过告警和日志定位；维护人员能按文档完成回滚。

## 阶段 5：持久化决策

**首版补偿方案：**继续使用进程内存储，明确告知玩家维护或重启后旧局失效，安排发布时避免打断正在进行的局；刷新时旧局失效应引导重新开局。

若试玩证明“重启后继续同一局”是必要需求，再单独设计持久化：同时保存牌局状态、事件、会话令牌、版本和幂等记录，定义过期与版本迁移方式，保证一次命令的状态提交与幂等记录一致。此时再选择数据库或其他适合的存储，不在首版预先引入。

**验收：**首版重启后页面给出准确失效提示；未来持久化版本需通过“出牌后重启服务、刷新并继续同一局”的测试。

## 推荐实施顺序与上线门槛

1. 先完成阶段 1 的资源保护，避免公开入口被无意或恶意占满。
2. 完成阶段 2 的自动对局、浏览器和并发验收，以测量值修订容量参数。
3. 完成阶段 3 的部署与阶段 4 的监控、回滚演练后，邀请少量用户试玩。
4. 根据试玩结果决定是否进入阶段 5 的持久化开发。

公开上线门槛：阶段 1～4 的验收项全部通过，具备 HTTPS、限流、牌局回收、故障发现和回滚能力。若使用中国大陆服务器及域名，还需按实际服务情况核实备案等要求。
